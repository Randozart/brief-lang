# DBriv Redesign Plan

**Date:** 2026-06-08 19:45
**Status:** Approved for implementation
**Supersedes:** `plans/active/DBRIEF_IMPLEMENTATION_PLAN.md`, `plans/active/DBRIEF_UNIVERSAL_DATA_ENGINE_PLAN.md`

---

## 1. Core Principle

**DBriv = native Briv data.** Import a `.dbv`/`.dbvl`/`.dbvs` file from Briv and it is immediately a native Briv value — no parsing step, no deserialization, no intermediate representation. `data.Item["rusty_key"].desc` just works. The compiler stores DBriv data as its own internal value representations.

This means:
- DBriv is **not** a struct/function declaration language — it is a data format
- Schemas provide field names + types + constraints; data files provide values
- The Briv optimizer consumes schema constraints as proven facts (preconditions for free)
- Query operations (`->FILTER`, `->MAP`, `->SORT`, aggregations) are Briv operations on native values

## 2. Syntax Reference

### 2.1 `.dbvs` — Pure Shape Declarations

```
// Field constraints: [condition] field_name: Type
schema Item {
    [ != "" ]   id: String       // constraint: id must be non-empty
    [ != "" ]   desc: String
    [ >= 0 ]    hp: Int
    takeable: Bool
    location: String
}

schema Room {
    [ != "" ]       name: String
    desc: String
    exits: Map[String, String]
}

// Enums are just schemas with a fixed set of string values
schema IoError {
    variant: String where in { "NotFound", "PermissionDenied", "AlreadyExists" }
}

// Struct-like composition
schema IoResult {
    success: Bool
    error: IoError
}

// FFI function signature shape (no address, no location, no backend metadata)
schema FnBinding {
    [ != "" ]   name: String
    params:     Vec[Type]
    returns:    Type
    language:   String
    dispatch:   UInt[8]
}
```

**Rules:**
- `schema Name { ... }` declares a named shape
- Field order determines positional matching order (for terse data)
- `[ != "" ]` before field = guard condition the data must satisfy (visible to Briv compiler)
- No `REGISTER`, no `ALIAS`, no `@address`, no `location` keyword
- `Map[K, V]` and `Vec[T]` for collection types
- Field types without `?` suffix are required; `field?: Type` is optional (skippable in positional form)

### 2.2 `.dbv` — Concrete Data

```
// Imports bring schema definitions into scope
import "game.dbvs"

// Positional form: key as Schema { val1, val2, val3, ... }
// Field names come from schema order
rusty_key as Item { "Rusty Key", "An old iron key", 5, true, "start" }
candle as Item { "Wax Candle", "A stubby candle", 3, true, "kitchen" }

// Named form: key as Schema { field1: val1, field2: val2, ... }
// Can skip optional fields
cheese as Item { name: "Moldy Cheese", desc: "Smelly.", hp: 1, location: "pantry" }

// Grouped by schema — schema name is the namespace
as Item {
    rusty_key { "Rusty Key", "An old iron key", 5, true, "start" }
    candle    { "Wax Candle", "A stubby candle", 3, true, "kitchen" }
}

as Room {
    cellar  { "The Cellar", "Dark and dusty...", { north: "kitchen" } }
    kitchen { "The Kitchen", "Smells like iron.", { south: "cellar" } }
}

// Schema-less — unknown shape, just keys and values
{ dom_state: "...", timestamp: 1234567890, raw: "<html>...</html>" }

// FFI bindings as data conforming to a schema
as FnBinding {
    print     { "print", [String], IoResult, "libruntime", 0 }
    read_file { "read_file", [String], Option[Data], "libruntime", 3 }
}

// Validation/query rules stored alongside data
rule can_go(from: String, to: String) {
    Room[from].exits -> contains(to)
}

rule visible_items(room: String) {
    Item -> FILTER location == room
}
```

**Rules:**
- `key as Schema { ... }` = keyed entry (access as `data.Schema["key"]`)
- `as Schema { ... }` = grouped entries (schema becomes namespace)
- `{ field: val, ... }` = schema-less object (keyed by first field or autogenerated)
- `rule name(params) { ... }` = named query (data is data)

### 2.3 `.dbvl` — Line Data

```
// Schema-typed — import defines column order
import "game.dbvs"

// id, desc, hp, takeable, location  (from Item schema field order)
rusty_key, "Rusty Key", "An old iron key", 5, true, start
candle, "Wax Candle", "A stubby candle", 3, true, kitchen

// Named casting for per-line schema override
key: value1, value2, value3, ...       // "key" identifies the entry

// JSONL — no schema, each line is self-describing
{"id": "cellar", "name": "The Cellar", "desc": "Dark and dusty..."}
{"id": "kitchen", "name": "The Kitchen", "desc": "Smells like iron."}
```

**Rules:**
- With schema: positional values per line, field order from schema
- Without schema (JSONL): each line is a complete object
- `key: val1, val2, ...` syntax for named entries in schema-typed mode
- Appending to `.dbvl` is always valid (runtime data logging)

## 3. Briv Integration

```briv
// Import a schema as a type
import Item from "game.dbvs"

// Import data as native Briv values
import data from "world.dbv"

// Direct field access — schema provides types
let desc = data.Item["rusty_key"].desc    // String
let hp: Int = data.Item["rusty_key"].hp   // Int (compiler-known type)

// Schema constraints are compiler-visible:
// Item.id satisfies [ != "" ] — compiler can elide emptiness checks

// Query rules are callable:
let visible = data.visible_items("cellar")

// Pipeline queries on native values:
let takeable_items = data.Item -> FILTER takeable == true
let item_names = data.Item -> MAP name
```

### Syntax/KW Features (removal from compiler)

| Feature | Removed From | Replacement |
|---------|-------------|-------------|
| `REGISTER` keyword | Lexer, parser | No such keyword; data matches a `schema` |
| `ALIAS` / `ALIAS?` keywords | Lexer, parser | No such keyword; plain data entries |
| `@` address syntax | Lexer, parser | Addresses are `UInt[64]` schema fields |
| `location:` field | Schema parser | FFI backend location is a field in the `FnBinding` schema |
| `DbrivAddress` (Numeric/Hex/Auto/Named/Remote) | AST | `UInt[64]` values |
| `DbrivRegister` AST node | AST | Data entries matching a schema |
| `DbrivAlias` AST node | AST | Gone entirely |
| `RULE head :- body` syntax | Parser | `rule name(params) { ... }` data entries |
| `DEPENDS` keyword | Parser | Gone (package management separate) |
| `SERVICE` keyword | Parser | Gone (moved to separate framework if needed) |
| `DbvsEngine` | `mod.rs` | Data is directly a Briv value |
| `DbrivEngine` | `mod.rs` | Same |
| `get_register()` / `get_alias()` | `mod.rs` | Imports resolve to native value access |

## 5. Implementation Phases

### Phase A: Syntax Spec + Parser Rewrite (Priority: HIGH)

**Goal:** New parser producing native Briv values directly, not an intermediate AST.

**Files to create:**
- `src/dbriv/parser.rs` (new, ~600-800 lines) — clean recursive-descent parser

**Files to delete:**
- `src/dbriv/ast.rs` (no longer needed; data = native Briv values)

**Tests:**
- Parse `.dbvs` with `schema`, field constraints, types
- Parse `.dbv` with positional, named, grouped, schema-less forms
- Parse `.dbv` with `rule` entries
- Parse `.dbvl` with schema-typed CSV and JSONL
- Parse `.dbvl` mixed with `key: val, val, val` casting
- Error cases: missing required field, constraint violation, unknown schema ref

**Deliverable:** `briv dbv <file>` outputs JSON confirming correct parse.

### Phase B: Briv Import Mechanism (Priority: HIGH)

**Goal:** `import data from "file.dbv"` populates native Briv values with schema-derived types.

**Files to modify:**
- `src/parser.rs` — add `.dbv`/`.dbvl`/`.dbvs` import resolution
- `src/typechecker.rs` — schema types become Briv types
- Import/symbol resolution — reading parsed data into value system

**Tests:**
- Import schema as type in Briv program
- Import data as native values
- Access `data.Schema["key"].field` from Briv
- Constraint propagation to optimizer
- Error: import of non-existent file, schema mismatch

### Phase C: Rewrite Library Files (Priority: MEDIUM)

**Goal:** All FFI bindings, hardware schemas, and target definitions use the new format.

**Files:** All `.dbvs`/`.dbv` files in `std/bindings/`, `lib/targets/`, `targets/`

**Tests:**
- All FFI functions still resolve correctly via new format
- Hardware handoff still generates valid output
- Target schemas still compile
- Integration: existing Briv programs that use `frgn` functions still work

### Phase D: Remove Old Code (Priority: MEDIUM)

**Goal:** Delete all vestigial code from the old design.

**Files to delete:**
- `alloc.rs`
- `schema_validator.rs`
- Old engine types in `mod.rs`
- Old AST types

**Files to clean:**
- `handoff.rs` — remove old-generation `extract_target_addresses`, `generate_dbvs`, `generate_dbv`
- `registry.rs` — remove `load_from_dbvs()`, old DBVS loading code
- `hardware_validator.rs` — remove `DbvsEngine`-dependent checks (replaced by import + native access)

**Tests:** Compiler builds, all tests pass, no dead code warnings.

### Phase E: Query Engine on Native Values (Priority: LOW)

**Goal:** The existing `eval.rs` query engine operates on native Briv values instead of `DbrivLiteral`.

**Tests:** All existing query operations (FILTER, MAP, SORT, COUNT, etc.) produce same results with native values.

### Phase F: `.dbvl` Append + Performance (Priority: LOW)

**Goal:** `.dbvl` files support runtime appending with zero-copy CSV line writing. Indexed lookups for large datasets.

**Tests:** Append 10k lines, query by key, verify performance.

## 6. Critical Path

```
Phase A (Parser) ──→ Phase B (Import) ──→ C (Rewrite libs)
      │                                         │
      └── Phase D (Delete old code) ←───────────┘
                      │
                      └── Phase E (Query engine)
                                   │
                                   └── Phase F (DBVL perf)
```

Phase A and B are the hardest and most consequential — get parser semantics right first. Phases C and D can run in parallel after B. Phase E and F are optimization/performance work once everything compiles and tests pass.

---

## 7. Success Criteria

1. `cargo test --lib` passes with all new parser + import tests
2. All FFI functions (`frgn print`, `frgn sqrt`, etc.) work identically through new `.dbv` binding files
3. `briv dbv <file>` parses and outputs correct JSON
4. `briv llvm` with hardware handoff generates valid `.dbv`/`.dbvs` in new format
5. Briv programs can `import` a `.dbv` and use its data as native values
6. Schema constraints are propagated to the Briv optimizer (provable via test)
7. Old `REGISTER`/`ALIAS`/`@address` code deleted — zero traces in compiler
8. `.dbvl` parse + append works for both schema-typed CSV and JSONL

## 8. Key Decisions Record

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Schema field order defines positional matching | Yes | Enables terse `.dbvl` lines — just provide values |
| Optional fields with `?` suffix | Yes | Allows skipping fields in positional form |
| Constraints on fields: `[ != "" ]` syntax | Yes | Symmetry with Briv contract brackets; compiler-visible |
| Rules as data entries, not separate extension | Yes | Keeps DBriv as "just data"; `.dbvr` not needed |
| No `REGISTER`/`ALIAS`/`@address` keywords | Yes | Pure data with schemas replaces all of them |
| FFI bindings as data matching `FnBinding` schema | Yes | No magic; users can see and customize bindings |
| Both positional and named forms in `.dbv` | Yes | Positional for terse; named for clarity/skipping |
| `.dbvl` supports both schema-typed CSV and JSONL | Yes | Covers both known-shape and unknown-shape use cases |
