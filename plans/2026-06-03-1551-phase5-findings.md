## Step 0: .gitignore `*.rs` Blockage

**Finding**: `*.rs` was a global pattern blocking ALL new `.rs` files including `src/**/*.rs`. This would silently prevent `git add` of any new Rust module.

**Fix**: Changed to `/*.rs` (root-level only). The `!src/hardware/handoff.rs` exception is no longer needed since `src/` files are not matched by `/*.rs`.

**Root cause**: Self-hosting generates `.rs` files at repo root (e.g., `main.rs`, `output.rs` from `brief rust --out .`). Those need ignoring; `src/**/*.rs` does not.

## Phase 5a: DBVS Import Parsing + Schema Type Validation

### Finding 1: `validate_schema_imports()` existed but was only wired in Verilog/VHDL paths
The `hardware_validator.rs` function was complete but `run_llvm_compile()` never called it. The LLVM backend had no awareness of schema types.

### Finding 2: DBrief types needed explicit mapping to Brief types
`DbriefType::Vector`, `Option`, `Result`, `Fn`, `Struct`, `Enum` have no Brief state-field equivalents. The `to_brief_type_name()` method returns errors for these so the compiler can emit diagnostics rather than silently treating them as `Int`.

### Finding 3: Schema type validation naturally lives in `LlvmBackend`
The backend already owns `build_field_index()` which knows every state field's type. Adding `validate_schema_types()` right after it gives a single pass that cross-references the schema alias map with the struct field map.

## Phase 5b: Auto-Target Resolution

### Finding: `.dbv` files import schemas via `IMPORT "name.dbvs"`
The auto-detection algorithm parses candidate `.dbv` files and matches their `IMPORT` statements against the program's `.dbvs` imports. The existing `kv260.dbv` imports `xck26.dbvs` — so any program with `import "xck26.dbvs"` auto-selects `kv260.dbv`.

### Finding: `process_target_dbv()` reuses existing infrastructure
No new address extraction was needed — the function already existed and was only called from the explicit `--target-dbv` path. Auto-detection just invokes it with a discovered path.

## Phase 5c: Schema ↔ Target Cross-Validation

### Finding: New module `src/analysis/schema_validator.rs` fits naturally next to `hardware_validator.rs`
The hardware validator checks program-level invariants (orphan variables, untriggerable txns). Schema validation checks schema↔target binding integrity (missing bindings, address overlaps). Both are "structural integrity" checks — separate concerns, same family.

### Finding: Address overlap detection uses base addresses only
Without HWH XML's `HIGHADDR` info, we can only detect same-base-address overlaps. The handoff generator does extract `high_address` from Vivado XML but `.dbv` target files store only the base. Full overlap detection would require the schema to carry size info.

## Phase 5d: Scoped MMIO Injection

### Finding: `mmio_prepopulated: bool` was a blunt instrument
The flag meant "ALL mmio_fields entries are valid for routing." But when schemas are imported, only schema-declared fields should route to MMIO. A state variable coincidentally named `gic_distributor` shouldn't accidentally become MMIO.

### Finding: The fix is defensive — remove non-schema fields from `mmio_fields` entirely
Not just skip them in `build_field_index()`, but actively `remove()` them from the map. Otherwise `emit_expr` and `emit_stmt` would still emit `inttoptr` + `volatile` for reads/writes to those fields.

## N3: Compile-Time PGO via Interpreter

### Finding: Real e-graph (egg crate) adds non-trivial compile overhead vs. lightweight alternative
The `egg` crate's e-class + e-node allocation and union-find costs O(iterations × rules × nodes). For most Brief programs the body expressions are simple arithmetic (a few dozen nodes). A lightweight recursive pass with fixpoint iteration (max 5 passes) covers the same optimization space at negligible cost.

### Finding: The simplification gate is critical
Without the gate (only applied when `optimize_budget > 0`), simplification runs even on trivial expressions like `a + b`. The gate makes it zero-overhead for everyday compiles and active only when the user opts in with `--optimize-budget`.

### Finding: Four simplification categories cover the practical space
1. **Identity elimination**: `x+0`, `x*1`, `x/1`, `x-0` → `x`
2. **Zero propagation**: `x*0`, `x&0` → `0`
3. **Negation elimination**: `!!x`, `-(-x)` → `x`
4. **Cancellation**: `(a+b)-b`, `(a-b)+b` → `a`
5. **Bitwise cleanup**: `x|0`, `x^0`, `x<<0`, `x>>0` → `x`

No `egg` crate dependency — ~200 lines total.
