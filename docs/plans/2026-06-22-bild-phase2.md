# Phase 2: Full BILD Support

**Date:** 2026-06-22
**Status:** Planned (not started)

## Overview

Phase 2 extends BILD from a minimal LLVM IR subset for primitives into a
full-featured low-level dialect that handles custom types, state access,
multi-output returns, contract verification, and debuggable error messages.

## P2-A: Custom Type Resolution in BILD

**Goal:** Every Brief type appearing as an `inop` parameter resolves to a
native LLVM type in BILD.

### Type resolution table

| Source Brief type | Resolved LLVM type | Mechanism |
|---|---|---|
| `type X = Int` | `i64` | Unwrap type alias in type→LLVM mapper |
| `meld T(f: Float)` | `float` | Lookup inner type via meld registry |
| `struct S { x: Int, y: Int }` | separate params `i64 %x, i64 %y` | Flatten struct fields into param list |
| `enum E { A, B, C }` | `i64` (discriminant only) | Unit enum → discriminant int |
| `enum E { A(Int), B(Float) }` | `(i64, i64)` (tag + payload) | Tagged union as two params |
| `Ptr<T>` | `i8*` | Already works |
| `&state.field` | N/A | See P2-D |

### Struct flattening rules

- Each struct field becomes a separate BILD register
- Field name is mangled as `%param_field` (e.g. `%p_x`, `%p_y`)
- Nested structs are recursively flattened
- The `term` register for struct-returning inops is a packed `{ i64, i64, ... }`
  or set of individual registers

### Enum layout

- **Unit variants** (no payload): `i64` discriminant, 0 = first variant, etc.
- **Payload variants**: `(i64 discriminant, i64 payload)`. Payload is the
  variant's data packed as `i64` or a pointer to heap-allocated data.
- The typechecker must verify BILD body matches the enum layout.

### Files to change

- `src/backend/llvm/mod.rs` — extend `llvm_type()` to resolve custom types
- `src/backend/llvm/emit_toplevel.rs` — `emit_inop()` must use resolved
  types instead of the current simple primitive mapping
- `src/typechecker.rs` — param type validation against `inop_decls` must
  handle aliases, melds, structs, enums

## P2-B: BILD Verifier (Better Error Messages)

**Current state:** Malformed BILD produces raw `llc` errors with LLVM line
numbers — no mapping back to the `.bv` source line.

### Three-tier approach

| Tier | What | Effort | Benefit |
|------|------|--------|---------|
| **1** | Shallow structural check: verify `term`/`term!` present, no undefined `%name` references, `;` terminators correct. Implemented as a walk on `InopDeclaration.llvm_body` after parsing. | Low | Catches 80% of common mistakes |
| **2** | Line mapping: when `opt`/`llc` fail, parse the `.ll` line number and map it back to the BILD source line range in the `.bv` file. The `.ll` output is emitted with `; <source line>` comments keyed to the parser's span. | Medium | Production debugging |
| **3** | Structured error capture: re-run `opt -passes=verify` on the emitted `.ll` and extract structured diagnostics from stderr. Present as `Error: BILD: undefined register '%x' at inop sadd (line 4)` | Medium | CI integration |

### Tier 1: Shallow structural checks

```rust
fn check_bild(inop: &InopDeclaration) -> Vec<BildError> {
    let mut defined: HashSet<&str> = HashSet::new();
    let mut errors = Vec::new();
    // All params are implicitly defined
    for (name, _) in &inop.params { defined.insert(name.as_str()); }
    // Walk body lines
    for (i, line) in inop.llvm_body.iter().enumerate() {
        if line.starts_with("term") { /* ok — terminates */ }
        else if let Some(rhs) = line.split('=').nth(1) {
            let lhs_name = line.split('=').nth(0)?.trim().strip_prefix('%')?;
            defined.insert(lhs_name);
            // Check each %register in rhs is defined
            for reg in find_registers(rhs) {
                if !defined.contains(reg) {
                    errors.push(BildError::UndefinedRegister(reg, i));
                }
            }
        }
    }
    errors
}
```

### Files to change

- `src/ast.rs` — add `BildError` enum and `InopDeclaration::check_bild()`
- `src/typechecker.rs` — call `check_bild()` after parsing in Pass 1
- `src/backend/llvm/mod.rs` — Tier 2: emit source-line comments in `.ll`
- `src/main.rs` — Tier 3: structured error capture from `opt`/`llc` stderr

## P2-C: BILD Contract Verification (Symbolic Execution)

**Goal:** Verify that the BILD body produces the same result as the fallback
expression (or satisfies the `[pre][post]` contract) without running the
full LLVM pipeline.

### Symbolic approach

Instead of full SMT-LIB bvlogic translation (months of work), Phase 2
implements a **symbolic interpreter for the BILD subset**:

1. Walk `InopDeclaration.llvm_body` and build a symbolic expression tree
   per register:
   ```
   %t1 = add i64 %a, %b    →    SymExpr::Add(SymVar("a"), SymVar("b"))
   term %t1                →    return value = SymExpr::Add(SymVar("a"), SymVar("b"))
   ```
2. Symbolically evaluate the fallback expression the same way:
   ```
   a + b                   →    SymExpr::Add(SymVar("a"), SymVar("b"))
   ```
3. Compare the two symbolic trees using structural equality
4. On mismatch, emit: `BILD body produces (a + 1) but fallback produces a`

### Supported LLVM instructions for symbolic execution

| Category | Instructions | Notes |
|----------|-------------|-------|
| Arithmetic | `add`, `sub`, `mul`, `udiv`, `sdiv`, `urem`, `srem` | All `i64` variants |
| Float | `fadd`, `fsub`, `fmul`, `fdiv` | `float` only |
| Bitwise | `and`, `or`, `xor`, `shl`, `lshr`, `ashr` | |
| Comparison | `icmp eq/ne/slt/sle/sgt/sge`, `fcmp oeq/olt/...` | |
| Conversion | `trunc`, `zext`, `sext`, `fptrunc`, `fpext`, `fptosi`, `sitofp` | |
| Select | `select` | |

Instructions NOT symbolically executed: `load`, `store`, `call`, `asm`,
`alloca`, `getelementptr`. These either require state access (P2-D) or
are opaque (call/asm). When encountered, the verifier emits a warning:
"cannot verify contract: BILD contains opaque operation at line N".

### Return-type contract verification

For inops with `[post]` contracts like `[sadd#(a,b) == a + b]`:

1. Symbolically execute BILD body → symbolic result `R`
2. Substitute `R` into postcondition: `[R == a + b]`
3. Normalize both sides and check structural equality
4. If equality holds, contract is verified
5. If not, emit `warning: contract [sadd#(a,b) == a + b] cannot be proven:
   BILD produces (a + b) but postcondition expects (a + b + 1)`

### Assumption-driven verification

For BILD bodies with opaque ops (call, asm, load), the verifier can
**assume the contract holds** and emit a note:

```
note: inop sadd at line 4: contract [sadd#(a,b) == a + b] assumed —
      BILD body contains inline assembly (opaque to symbolic execution)
```

This is correct because the user wrote the contract intentionally.
The symbolic verifier's job is to catch accidental mismatches, not to
prove everything.

### Files to change (new module)

- `src/analysis/bild_symexec.rs` — symbolic interpreter for BILD subset
- `src/proof_engine.rs` — call bild_symexec when contract involves
  `UserDefined` intrinsics
- `src/ast.rs` — `SymExpr` enum for symbolic expression trees

## P2-D: %state Access

**Goal:** Allow inops to read and write program state fields directly.

### Syntax

```brief
inop! tick_counter() -> Int (%state) {
  %ptr = getelementptr inbounds %State, %State* %state, i32 0, i32 11
  %val = load i64, i8* %ptr
  %inc = add i64 %val, 1
  store i64 %inc, i8* %ptr
  term %val;
} fallback 0;
```

The `(%state)` marker on the signature signals that the BILD body receives
the `%State*` pointer as its first parameter. Without it, the pointer is
not passed (Phase 1 behavior, unchanged).

### Safety rules

| Rule | Rationale |
|------|-----------|
| Must be `inop!` | State mutation is a side effect — `inop` (pure) would be a lie |
| State accesses must be to live fields | Dead-field elimination removes unused fields; accessing a dead field is undefined |
| Contract `[pre][post]` required | Compiler uses contract to reason about state effects |
| Field offset must match LLVM struct layout | The `i32 0, i32 N` GEP indices correspond to the `%State` struct layout emitted by `emit_toplevel.rs`. A mismatch crashes at runtime. |

### Field offset resolution

The Brief compiler knows the `%State` struct layout. For Phase 2, the user
writes raw GEP indices. A Phase 3 improvement would allow named field
references:

```brief
inop! read_counter() -> Int (%state) {
  %val = load state.counter, i64
  term %val;
}
```

This would resolve `state.counter` to `getelementptr %State, %State* %state,
i32 0, i32 <counter_index>` using the same layout as `emit_toplevel.rs`.

### Liveness implications

When `inop!` declarations exist, the liveness analysis must mark their
accessed fields as live. Currently, dead-field elimination assumes only
reactive transactions access state. With `%state`-accessing inops, the
compiler must:

1. Collect `state.field` references from all `%state`-accessing inops
2. Add them to the live field set during `compute_live_fields()`
3. Never eliminate a field that an inop reads or writes

### Files to change

- `src/backend/llvm/emit_toplevel.rs` — detect `(%state)` marker and pass
  `%State* %state` as first param to `emit_inop()`
- `src/ast.rs` — add `has_state_access: bool` to `InopDeclaration`
- `src/parser.rs` — parse `(%state)` marker after `-> Type`
- `src/analysis/transition_graph.rs` — mark inop-accessed fields as live
- `src/typechecker.rs` — enforce `inop!` + contract requirement

## P2-E: Multi-Output Inops

**Goal:** Allow inops to return multiple values.

### Syntax

```brief
inop divmod(a: Int, b: Int) -> (Int, Int) {
  %q = sdiv i64 %a, %b;
  %r = srem i64 %a, %b;
  term %q, %r;
}
```

### Lowering

The compiler detects multiple registers after `term` and emits an LLVM
struct return:

```llvm
define { i64, i64 } @divmod(%State* %state, i64 %a, i64 %b) {
  %q = sdiv i64 %a, %b
  %r = srem i64 %a, %b
  %ret = insertvalue { i64, i64 } undef, i64 %q, 0
  %ret2 = insertvalue { i64, i64 } %ret, i64 %r, 1
  ret { i64, i64 } %ret2
}
```

### Call site

```brief
let (q, r) = divmod#(10, 3);
```

The typechecker handles tuple destructuring of `UserDefined` calls when
the return type is a tuple.

### Files to change

- `src/ast.rs` — support multi-register `Term %q, %r` in BILD parsing
- `src/parser.rs` — handle comma-separated registers in `term` inside
  BILD body (separate from the `term` statement in Brief's statement
  parser)
- `src/backend/llvm/emit_toplevel.rs` — detect multi-register `term` and
  emit struct return
- `src/backend/llvm/emit_expr.rs` — handle multi-output `UserDefined`
  calls with `extractvalue` on the caller side
- `src/typechecker.rs` — tuple destructuring for inop calls

## Open Questions for Discussion

1. **Struct flattening**: Every field as a separate BILD register, or a
   packed `i8*` pointer for manual GEP? Flattening is explicit and
   debuggable but verbose for deep nesting.

2. **Enum layout**: `(i64 tag, i64 payload)` with payload packed, or
   unpack the payload fields individually (matching struct flattening)?

3. **Symbolic BILD vs full SMT-LIB**: Symbolic execution (pragmatic,
   implementable in one sprint) catches mismatches between BILD body and
   fallback. Full SMT-LIB bvlogic translation would enable formal proofs
   but requires months of work. Recommendation: symbolic execution now,
   SMT-LIB as Phase 3.

4. **`%state` safety inference**: Should the compiler auto-detect `%state`
   pointer access in the BILD body and enforce `inop!` automatically, or
   require the user to write `(%state)`? Recommendation: explicit `(%state)`
   marker — keeps the language predictable.
