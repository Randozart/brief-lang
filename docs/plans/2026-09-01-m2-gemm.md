# Plan: M2 GEMM — the metadata thesis at full strength

**2026-09-01.** Successor to the GEMV arc (M1 beats the ggml anchor batched:
0.205ms / 163 GFLOP/s on the 3060 vs ggml's 0.213ms on their 20GB CUDA

## The thesis, stated

ggml hand-writes a GEMM kernel per architecture. Briev's .abv expresses
NAIVE matmul and the compiler derives the tuned kernel — because the
metadata (static shapes, the reactive contract, the state layout) lets the
ANALYSIS prove what a C compiler cannot see: which loops tile, which
operands are read-only, which bounds are exact. If M2 lands, the user
source stays the 15-line foreach; the kernel evolves to hand-tuned class.

## M2.0 — naive correctness (TODAY's finding: two holes, both real)

`examples/gpu/gemm.abv` (M=N=K=4096, body: `m=i/N; n=i%N; foreach k:
acc += a[m*K+k] * b[k*N+n]`) compiles — WRONG in two ways:

1. **Silent vec4 misalignment**: the cooperative vec4 gate checked
   count%4==0 + member offset%16==0 but NOT the INDEX alignment. For
   `b[k*N + n]`, the substituted base `(lane*4 + t*128)*N + n` is not
   4-divisible (n is arbitrary) — the `>>2` reads the wrong element.
   GEMV passed only because its indices are affine with 4-divisible
   coefficients. Fix: the vec4 collector must PROVE
   `(index with k:=0) mod 4 == 0` (const-folded; products provable when
   either factor ≡0 mod 4; conservative reject otherwise) — b falls back
   to scalar loads inside the same kernel.
2. **Cooperative over-fire**: the GEMV recognition requires the item id to
   BE the row (`a[i*K+k]`, `y[i]`). GEMM decomposes the item id
   (`m=i/N, n=i%N`) — the cooperative row kernel bound `row = gid>>5` and
   dispatched (32, M*N) = 32× the needed threads. Fix: the shape gate
   rejects the cooperative form when the counter is decomposed
   (division/modulo of the index var in the body); GEMM takes the flat 2D
   path (`work_cols = N`).

Gate: gemm_small.abv (64³) exact vs double reference; then the 4096³
timing row (naive — expected terrible: B is strided K*4 bytes apart).

## M2.1 — compiler tiling (the rung's core)

The analysis rewrites the recognized GEMM shape into a tiled kernel:
workgroup computes a TILE_M × TILE_N block of y through shared memory
(Workgroup storage class + OpControlBarrier — NEW kernel-emission
machinery: shared-memory allocas, barrier emission, cooperative loads).
Tile sizes derived from the STATIC shapes (metadata: K, N are consts).
Gate: 4096³ within 4× of the ggml-cuda GEMM anchor (new anchor bench
needed: ggml_gemm_bench.c, A(4096×4096) × B(4096×4096)).

## M2.2 — cooperative matrix (tensor cores, endgame)

VK_KHR_cooperative_matrix on Ampere+: OpCooperativeMatrixMulAdd — the
analysis's tile proof decides when the transform is legal; the backend
emits Mma ops. Target: >=50% of cuBLAS-class fp32 on the 3060 (~13 TFLOP
peak SIMT / ~25 TFLOP tensor). This is the row where "Briev has more
metadata" either shows or doesn't: ggml must ship this per-arch; the .abv
user writes foreach and gets it from a shape proof.

## M2.0 verdict (2026-09-01, same session — both holes fixed, latent bug found)

- Hole 1 fixed: `collect_vec4_indices` now PROVES `(index with loop var
  ≡0) mod 4` via `expr_provably_mod4_zero` (products: either factor;
  sums: both; div/mod/call: reject). GEMM's `b[k*N+n]` falls back to
  scalar loads through the vec4-typed member's shifted-scalar access.
- Hole 2 fixed: `kernel_stmts_decompose_counter` rejects the cooperative
  form when the counter is decomposed (div/mod of the index var); GEMM
  emits the flat LocalSize-256 kernel. The decision is CENTRALIZED in
  `is_cooperative_shape` — kernel emission and the runner's dispatch
  geometry consume ONE predicate (the M2.0 bug where they drifted:
  flat blob + cooperative dispatch = 256x redundant work).
- **LATENT BUG found and fixed** (`emit_vec4_fma_group` runtime form):
  the vec4 base was `div4(zeroed) + (kv − loop_start)/4` — missing the
  `+ loop_start/4` anchor. Every runtime iteration read the vec4 block
  from the loop's START, re-summing the unrolled prefix and shifting the
  a/b pairing by the prefix. Diagnosed with an identity-matrix probe
  (y = b[n] + b[n+4] exactly — the (n+4)%5 fingerprint of element
  offset 16 = the prefix). **The non-cooperative GEMV has been silently
  wrong since O3 landed** — masked because the cooperative default took
  over M1; post-fix it verifies exact (0.887ms serial row).
- Results: gemm 64³ exact; **4096³ exact at ~778ms (175 GFLOP/s)** —
  naive is B-strided (one useful float per cacheline); M2.1's tiling is
  the whole game. ggml anchor for GEMM still needed (ggml_gemm_bench.c).
