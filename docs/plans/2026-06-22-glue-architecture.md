## 1. Vision

GLUE is a universal FFI broker. Any two languages that consume or produce LLVM-compatible object code can be linked through GLUE. Neither language knows Brief exists. Both see their own native interface. Brief is the invisible translator using `meld` to prove type compatibility at compile time — zero serialization, zero allocation at the call boundary. No C compiler, no `extern "C"`, no `cc` crate — the bridge IS native object code.

### One-Sentence Thesis

A Rust developer writes `use bridge::process_data` — it's a Rust crate.  
A Python developer writes `from bridge import process_data` — it's a native module.  
A Node developer writes `const bridge = require('bridge')` — it's a JS addon.  
All three call the **same** Brief bridge. All three think they're talking to their own language.

## 2. Architecture

```
Language A sources ──→ [Language A compiler] ──→ .o / .so
                                                      │
                                                      ▼
Language B sources ──→ [Language B compiler] ──→ .o / .so ──→ GLUE bridge (.a / .so / .wasm)
                                                      ▲
                                                      │
                                                Bridge (.bv)
                                                Define frgn, #export, meld
```

The bridge is a Brief program that:

| Component | Role | Brief syntax |
|---|---|---|
| **`#export`** | Exposes functions to Language A. Language A sees native functions. | `defn #export "name" fn(a: Int) -> Int { ... };` |
| **`frgn`** | Declares calls into Language B. Language B provides these as native exports. | `frgn fn_from_B(x: Int, y: Int) -> Int;` |
| **`meld`** | Proves types on both sides share identical bits. Zero-copy guarantee. | `meld StructA <:> StructB;` |

### Calling convention

The bridge compiles to a **shared library** (`.a`/`.so`/`.wasm`). Every `#export` function becomes a public symbol. Every `frgn` declaration remains an unresolved symbol — the foreign library provides them at link time.

**No C code required.** The bridge object file IS the native object file. Language A links it directly. Language B links it directly. Brief is the middle layer.

### Language matrix

Every language that can consume LLVM-compiled object code can link a GLUE bridge directly — no C ABI layer needed. The bridge `.a`/`.o`/`.wasm` IS native code in the target's object format.

| Language | Links LLVM object code natively? | GLUE bridge format |
|---|---|---|
| **Rust** | ✅ `rustc` consumes `.o` directly via its LLVM backend | `.a` linked via `rustc` — no `extern "C"`, no `cc` crate |
| **C / C++** | ✅ `clang`/`gcc` consume `.o` directly | `.o` linked via the system linker |
| **Zig** | ✅ `zig` consumes `.o` via LLVM backend | `.o` linked directly |
| **Go** | ⚠️ Go has a custom linker but can consume `.o` via `cgo` | `.o` via cgo wrapper generated by adapter |
| **WASM** | ✅ LLVM → WASM directly | `.wasm` — no C, no linker |
| **Python** | ✅ CPython loads `.so` (same format as LLVM emits) | `.so` via CPython extension adapter |
| **Node/JS** | ✅ N-API `.node` addon (same object format) | `.node` via N-API adapter |
| **Java** | ✅ JNI `.so` | `.so` via JNI adapter |

The bridge object file uses **whatever ABI the target linker expects**. For Rust, that's Rust's native ABI (same as any other `.o` produced by `rustc`). For Python, that's CPython's extension ABI. No C anywhere in the chain.

## 3. Data Brief Formats: `.dbv`, `.dbvs`, `.dbvl`

### `.dbv` — Data Brief (universal data, container)

The universal data extension. Less strict — a container for data organized under Data Brief rules. Used for configurations, struct definitions, and any structured data. The `V` stands for "Brief" (a silly abbreviation), not "Variant."

### `.dbvs` — Data Brief Schema

Defines the grammar for validating `.dbv` and `.dbvl` files. Semicolon-terminated declarations inside `entry Name { ... };` blocks.

**Field types:**

| Type | Example | Description |
|---|---|---|
| `String` | `name: String;` | A text value |
| `Int` | `count: Int;` | An integer |
| `Enum<A, B, C>` | `link: Enum<static, dynamic>;` | One of the listed values |
| `List<T; delimiter=X>` | `exts: List<String; delimiter=space>;` | Space-separated list of values |
| `Map<K, V; ...>` | `types: Map<String, String; pair_separator=:, value_delimiter=space, brace=required>;` | Curly-brace-delimited key:value pairs, space-separated |
| `Optional<T>` | `build: Optional<String>;` | May be absent |

**Example — `glue.dbvs`:**

```dbvs
entry GlueAdapter {
    lang: String;
    exts: List<String; delimiter=space>;
    link: Enum<static, dynamic>;
    types: Map<String, String; pair_separator=:, value_delimiter=space, brace=required>;
    templates: String;
    build: Optional<String>;
};
```

### `.dbvl` — Data Brief Lines

Raw data, one entry per line. Each line is self-contained — appendable, streamable, no nesting.

**Parsing rules:**

1. Split file by newlines → lines
2. Blank lines and comment lines (starting with `//`) are skipped
3. If line starts with `schema <path>;`, load the `.dbvs` schema and activate it for subsequent lines
4. Otherwise, split the line by `,` (respecting `" "` quoted strings and `{ }` map blocks)
5. If an active schema is set, validate field count + types against it
6. If no active schema, return raw string vectors (scraping mode)
7. Multiple schema switches are allowed mid-file — each `schema <path>;` line sets the active schema from that point forward

**Quoting rules:**

| Case | Example | Rule |
|---|---|---|
| Simple value | `rust` | No quotes |
| Value with comma | `"my, weird lang"` | Quotes required |
| Map | `{Int:i64 Float:f32}` | Braces protect internal commas |
| Empty field | `(nothing)` | Empty string |

**Example — `glue.dbvl`:**

```dbvl
schema glue.dbvs;
rust, rs, static, {Int:i64 Float:f32 Bool:bool}, templates/rust/
python, py so, dynamic, {Int:int Float:float String:str}, templates/python/
node, js d.ts, dynamic, {Int:number Float:number}, templates/node/
cobol, cbl cpy, dynamic, {Int:PIC S9(18) COMP}, templates/cobol/
```

## 4. CLI Verbs

### `brief link <path> <function>` — Import a foreign function into Brief

```
brief link libfoo.so "process_data"
```

1. Analyzes the foreign library (reads symbol table, finds `process_data`)
2. Cross-references against `src/ast.rs:477+` Intrinsic enum — if `process_data` matches an intrinsic name, use `intrinsic_call#()` instead of `frgn`
3. Generates a `.bv` file with appropriate `frgn` or `intrinsic_call#()` declaration
4. Optionally generates a `bindings.toml` for the FFI registry
5. The user can now call `process_data#()` or `process_data(args)` from Brief

### `brief export <bridge.bv> <language>` — Compile Brief as a native library

```
brief export bridge.bv rust
```

1. Compiles `bridge.bv` with `--library` flag (no `main` function emitted)
2. Reads `glue.dbvl`, finds the entry for `<language>`, validates against `glue.dbvs`
3. Loads the adapter template directory for that language
4. Generates native wrappers using the template engine
5. Output: `glue/<language>-bridge/` directory containing the complete native package

### `glue <target> <function> <language>` — One-shot universal wrapper (standalone CLI)

```
glue libfoo.so "process_data" rust
```

1. Does `brief link` internally to generate the `.bv` wrapper
2. Does `brief export` internally to compile and generate the native crate
3. Output: complete native package that calls `process_data` from `libfoo.so`
4. The developer adds `use glue_bridge::process_data` — that's it.

## 5. Memory Model

Three tiers, implemented from the start:

### Tier 1: Register-passing (zero allocation)

Types that fit in registers:

| Type | Width | Passed as |
|---|---|---|
| Int | 64-bit | i64 register |
| Float | 32-bit | float register |
| Bool | 1-bit | i8 (zero-extended to i64) |
| Struct ≤ 16 bytes | 128-bit | Two i64 registers or one SSE register |

No allocation. No `__glue_release` needed.

### Tier 2: Arena stacks (heap-allocated returns)

For Strings, large structs, and return values that don't fit in registers:

1. Bridge allocates on its **per-call arena** before calling the `#export` body
2. The `#export` function writes the return value into the arena
3. Caller receives a pointer to the arena
4. Caller reads the value
5. Caller calls `__glue_release(frame_tag)` — the arena is freed as a batch

Arenas are stack-allocated (chunked linked list). For nested calls (bridge → foreign → bridge → foreign), each call gets a new arena frame. When the inner call returns, its frame is released — the outer frame survives. Total memory bounded by call depth × max allocation per call.

**`__glue_release` protocol:**

```c
// Called by the foreign language after reading a heap-allocated return value.
// frame_tag identifies which arena frame to release.
// Passing 0 releases the entire GLUE arena stack.
void __glue_release(uint64_t frame_tag);
```

The generated adapter handles this transparently. The foreign language developer never calls `__glue_release` directly — the native wrapper (`lib.rs`/`__init__.py`/`index.js`) does it.

### Tier 3: Shared memory regions (zero-copy via meld proof)

Negotiated during `__glue_init()`:

1. Bridge and foreign language agree on a shared memory region
2. `meld` proves both sides interpret the same bytes identically
3. The `#export` function reads/writes directly in the shared region
4. No allocation at the call boundary
5. Zero-copy — `meld` proof guarantees correctness

**`__glue_init` protocol:**

```c
// Called once when the bridge is loaded. Returns the frame_tag for the base arena.
// The foreign language may pass a pointer to a shared memory region via shm_ptr.
uint64_t __glue_init(void* shm_ptr, uint64_t shm_size);
```

## 6. Adapter System

Each language adapter is a template directory + one entry in `glue.dbvl`.

### Template directories

```
templates/rust/
  Cargo.toml.hbs
  build.rs.hbs
  lib.rs.hbs
  ffi.rs.hbs          (unsafe extern "C" — not exposed to user)

templates/python/
  setup.py.hbs
  bridge_module.c.hbs  (CPython extension boilerplate)
  __init__.py.hbs

templates/node/
  package.json.hbs
  binding.gyp.hbs
  index.js.hbs
  index.d.ts.hbs

templates/cobol/
  bridge.cbl.hbs
  bridge.cpy.hbs
```

### Adapters are Brief `$!` macros (not a separate template engine)

Each language adapter is a `.bv` file containing `$!macro` definitions. The macro
receives the bridge's `#export`/`frgn`/`meld` declarations at compile time and
emits native wrapper source code for the target language.

```bv
// glue/adapters/rust.bv — Rust adapter macro

$!macro glue_bridge_rust(exports: Vec<ExportDecl>, frgns: Vec<FrgnDecl>, types: TypeMap) {
    // Generate Cargo.toml
    compile#("Cargo.toml", format!(
        "[package]\nname = \"{}\"\nversion = \"0.1.0\"\nedition = \"2021\"\n",
        bridge_name
    ) + "[dependencies]\n" + generate_dependencies(types));

    // Generate lib.rs with safe wrappers for each #export
    for export in exports {
        compile#("src/lib.rs", format!(
            "pub fn {}({}) -> {} {{\n    unsafe {{ ffi::{}({}) }}\n}}\n",
            export.export_name, export.params, export.ret_ty,
            export.export_name, export.param_names
        ));
    }

    // Generate ffi.rs with extern "C" block (not exposed to user)
    // The extern "C" block is emitted by the macro — it matches the
    // bridge's object file symbols directly. No C compiler involved.
    compile#("src/ffi.rs", generate_ffi_block(exports, frgns));
};
```

The macro uses `compile#()` (a compile-time intrinsic) to write generated
source files alongside the compiled `.a`. The files are ready to use as
a self-contained native package.

**Language adapter directory:**
```
glue/adapters/
  rust.bv       ← $!macro glue_bridge_rust(...)
  python.bv     ← $!macro glue_bridge_python(...)
  node.bv       ← $!macro glue_bridge_node(...)
  cobol.bv      ← $!macro glue_bridge_cobol(...)
```

Adding a language = writing one `.bv` macro file. No compiler rebuild,
no new parsers, no separate template language.

### Template variables (for reference, used inside macros)

| Variable | Source | Description |
|---|---|---|
| `{{bridge_name}}` | `.bv` filename | Name of the bridge |
| `{{exports}}` | `#export` declarations | Generated for each exported function |
| `{{types}}` | `glue.dbvl` type map | Brief type → native type conversions |
| `{{frgn_decls}}` | `frgn` declarations | Generated for each foreign function call |
| `{{intrinsics}}` | AST Intrinsic enum + user `frgn` | Cross-referenced: if `frgn` matches intrinsic, emit `intrinsic_call#()` instead |

### The intrinsic cross-reference

When the template engine processes a `frgn` declaration, it checks against `src/ast.rs:477+` Intrinsic enum:

```rust
fn is_intrinsic(name: &str) -> bool {
    matches!(name, "print_int" | "print_float" | "put_char" | "strlen" | "get_env_int"
                  | "read_stdin" | "get_global_id" | "get_local_id" | /* ... full list */)
}
```

If the `frgn` name matches an intrinsic, the template emits `intrinsic_call#(args)` instead of `call @name(args)`. This cleanup applies to both `brief link` (generates correct `.bv`) and the template engine (generates correct native wrappers).

## 7. Error Propagation (The Airlock)

Brief's `frgn` always returns a typed result — either the expected type or a `Result<T, E>`. When a `frgn` call inside the bridge fails:

### The rule: "Always be prepared to handle null"

The GLUE docs document this as the first law. Every caller must handle the case where the bridge returns null / zero / empty — whatever the return type's zero value is.

| Return type | Bridge failure behavior | Caller sees |
|---|---|---|
| `Int` | Returns `0` | Integer zero — same as a C "return 0" |
| `Bool` | Returns `false` | False |
| `String` | Returns null pointer | Caller should null-check |
| `*const T` | Returns null pointer | Caller should null-check |
| `Result<T, E>` | Returns `Err(glue_error)` | Caller gets the error — must match |

The bridge never panics. It always returns a valid value for the return type. The zero value convention maps to what the target language already considers "something went wrong" — C returns -1 or null, Rust returns `None` or `Err`, Python raises an exception, JS returns `undefined`.

### How the adapter generates error handling

```rust
// Generated lib.rs (Rust adapter)
pub fn bridge_fn(x: i64, y: i64) -> i64 {
    let result = unsafe { ffi::bridge_fn(x, y) };
    // If result is i64::MIN, the bridge encountered an error.
    // The bridge always returns a valid i64 — but signals errors
    // through the convention documented in GLUE.md §Error Handling.
    result
}
```

For languages with exception/result types (Rust, Python, Java), the adapter CAN convert error signals into native error types — the `.dbs` schema for the language specifies how. The default is the zero-value convention. The bridge ALWAYS returns something valid.

## 8. frgn → Intrinsic Cleanup

The codebase has `frgn` declarations that should be `intrinsic_call#()` calls. Every `frgn` name that matches an `Intrinsic` variant in `src/ast.rs` should be replaced.

### Where this applies

| File | Pattern | Action |
|---|---|---|
| `lib/std/string.bv` | Various `frgn` string ops | Check each against `Intrinsic` enum |
| `lib/std/io.bv` | `frgn __read_file` etc. | No intrinsic exists — keep as `frgn` |
| `lib/std/env.bv` | `frgn __get_env_int` | Check if `get_env_int#` exists as intrinsic |
| Any user `.bv` with `frgn` | Declared in code | GLUE `brief link` auto-detects and upgrades |

### GLUE's role

Both `brief link` and the template engine cross-reference against the Intrinsic enum:

```
IF frgn_name ∈ Intrinsic enum:
    emit intrinsic_call#(frgn_name, args)
ELSE:
    emit call @frgn_name(args)
```

This is automatic. The user never thinks about it.

## 10. The GLUE Engine (`glue-ffi`)

A standalone repository at `~/Desktop/Projects/glue-ffi/` that implements GLUE outside of the Brief compiler.

### Relationship to the compiler

```
brief-compiler/src/glue/         ← In-tree GLUE module (compiler built-in)
~/Desktop/Projects/glue-ffi/     ← Standalone GLUE engine (published separately)
```

The standalone GLUE engine:
- Works identically to the compiler's built-in GLUE
- Is published as a separate binary + library
- Requires the Brief compiler to be installed (documents this)
- Is for users who want to link two non-Brief languages without using the Brief compiler directly

### Distribution

```
glue-ffi/
  Cargo.toml         ← Standalone Rust project
  src/
    main.rs          ← CLI entry point (same verbs)
    glue.rs          ← Reuses src/glue/ from brief-compiler
    dbvl_reader.rs    ← Reuses dbvl_reader from brief-compiler
    dbvs_validator.rs ← Reuses dbvs_validator from brief-compiler
    adapter.rs       ← Template engine
    link.rs          ← Library analysis + .bv generation
  templates/         ← Same template directory structure
    rust/
    python/
    node/
    cobol/
  lib/
    glue.dbvl        ← Same adapter registry
    glue.dbvs        ← Same schema
```

The standalone GLUE depends on `brief build` being available on `$PATH`. When the user runs `glue libfoo.so process_data rust`, it internally calls:

```
brief link libfoo.so "process_data"    # generates .bv
brief export bridge.bv rust            # compiles to crate
```

## 11. Self-Hosting Path

GLUE is the bridge from Rust-compiler to Brief-compiler.

```
Phase A (today):    Rust compiler → LLVM C API + extern "C" FFI
Phase B (M5):       Rust compiler → GLUE bridge → frgn → Rust impl
Phase C (M6):       Rust compiler → GLUE bridge → frgn → Brief impl
Phase D (M7):       Brief compiler (via GLUE bridge) → frgn → Brief impl
Phase E (final):    Brief compiler (native, no Rust shell)
```

| Phase | What changes | Proof |
|---|---|---|
| **A** | Status quo | All tests pass |
| **B** | One `fn simplify()` replaced with GLUE bridge calling back into Rust | All tests pass, identical output |
| **C** | Replace `frgn __simplify_impl` with pure-Brief `simplify()` implementation in the bridge | All tests pass, identical output |
| **D** | Replace compiler's typechecker pass with GLUE bridge → Brief typechecker | All tests pass |
| **E** | Compiler `main.rs` is just `bridge::run()` — everything else is a GLUE bridge | Self-hosting achieved |

Each phase is independently testable. Phase B is the critical proof that GLUE works end-to-end with actual compiler code.

### End-to-end test

A Rust program that links a GLUE bridge and calls a `#export` function:

```rust
// tests/e2e_bridge.rs
use glue_test_bridge;

#[test]
fn test_bridge_call() {
    let result = glue_test_bridge::process_data(42, 7);
    assert_eq!(result, 49);
}
```

The bridge is compiled from:

```brief
// tests/e2e_bridge.bv
frgn add(a: Int, b: Int) -> Int;

defn #export "process_data" process_data(x: Int, y: Int) -> Int {
    term add(x, y) + 1;
};
```

The `add` function is provided by a small C file:

```c
// tests/e2e_bridge.c
int64_t add(int64_t a, int64_t b) { return a + b; }
```

The C file is linked with the bridge `.a` into the test binary. The Rust test calls `process_data` → bridge → `frgn add` → C. No C headers, no `#[link]`, no `extern "C"` visible to the Rust test.
