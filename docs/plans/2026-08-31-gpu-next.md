### Verdicts on the O-ladder (§6)

| rung | verdict | reasoning |
|------|---------|-----------|
| O2 FMA fusion | **do as planned** — explicit beats "usually" | The NVIDIA driver usually contracts `a*b+c`, but "usually" is not a proof, and fused vs unfused changes numerics (matters for the bit-exact discipline). Emit `GLSL.std.450 Fma` via ExtInstImport. Nearly free. |
| O3 float4 loads | **do, but gated on evidence** | The lever is coalesced wide loads, not `OpTypeVector` per se. Volta+ gets much of the benefit from coalesced scalar loads via the driver vectorizer. Only add float4 if the M1/O2 profile shows memory stalls; use `OpDecorate Alignment` on SSBO members rather than ad-hoc proof threading. Alignment proof: `offset % 16 == 0` AND trip count divisible by 4, else scalar. |
| O4 shared-memory tiling | **right idea, wrong benchmark** | GEMV gets nothing from shared memory (no in-group reuse; broadcast is a hardware feature). If the ladder's endpoint is GEMM (cuBLAS territory), tiling + register blocking is mandatory; but M1's ledger target is GEMV (llama.cpp territory). Decide the endpoint before building O4. |
| O5 LocalSize | **config default + existing probe, not a compile-time search** | 64×1×1 is almost certainly wrong for GEMV (want 128–256). But a compile-time "LocalSize search" is a GPU auto-tuning probe — reuse the existing probe infrastructure from the `.bv` lane instead of a heuristic. Config default, probe override. |
| O6 shared-memory tree reductions | **replace with subgroup ops** | Vulkan 1.3 (our target env) mandates subgroups. `OpGroupNonUniformFAdd` beats a shared-memory tree on every modern GPU: no barriers, no bank conflicts. Shared-memory reduction is the pre-2015 answer. |

### What the ladder is missing

1. **Split-K for GEMV** — for K=4096, one dot product per work item leaves
   most SMs idle when M is small. Partition K across workgroups + a second
   tiny reduction kernel. This is the single biggest GEMV lever on a 28-SM
   3060 and llama.cpp does exactly this. Absent from the ladder.
2. **Arithmetic-intensity-driven probe** — §4 found the territory boundary
   ("compute-dense + device residency"). Formalize: the frontend computes
   intensity per kernel; the `.bv` probe *verifies* the intensity-predicted
   decision instead of exploring. The honest version of "Max Efficient
   Default" for the GPU lane.
3. **Kernel fusion across phases** — each host-owned phase boundary is a
   launch + sync. If the dependency analysis proves two back-to-back kernel
   phases share no host-visible scalar, fuse them (or grid-stride them in
   one launch). Standard practice (Triton/XLA); collapses nbody's
   launch-bound regime into compute-bound. Fits frontend-driven dispatch
   perfectly.
4. **2D dispatch over div/rem** — the 64-bit div/rem blocker (§4) is better
   removed than lowered: `gid.y = row` in a 2D dispatch eliminates the
   division entirely. Magic-number division (Granlund–Montgomery) is the
   fallback for cases that genuinely need 1D.
5. **Persistent kernels** (backlog, not scheduled) — a kernel that loops
   internally on a device-side flag eliminates launch overhead entirely.
   The natural endgame of the `.abv` resident model; only worth it if
   residency (handoff §5.4) still leaves launch overhead dominant.

## 2b. 2D dispatch — design notes (decided, ready to implement)

Key insight: the kernel does NOT need the body rewritten. The work item
id `i` can be *reconstructed linearly* from a 2D GlobalInvocationId
(`i = gid.y * width + gid.x`, `width = LOCAL_SIZE_X * groups_x`), so the
launch shape changes while the body keeps its scalar `i` — no body
rewriting, no new eligibility rules. The row/col decomposition the user
writes by hand (`i >> 12`, `i & 4095`) keeps working on the
reconstructed `i`; a later frontend pass may then RECOGNIZE the
shift/mask pattern and substitute `gid.y`/`gid.x` directly, removing the
ops entirely (that recognition is frontend-driven dispatch, config off
by default until proven).

Stages:
1. Runtime: `briev_accel_launch2d(idx, state, nx, ny)` in
   `briev_accel_rt.c` + `launch_dev` 2D in `briev_dev_vulkan.c`
   (`vkCmdDispatch(groups_x, groups_y, 1)`; groups_x = ceil(nx/64),
   groups_y = ny). OpenCL equivalent (`NDRange` is natively 2D).
2. Lowering: kernel entry emits `i` from `gid.y * width + gid.x` when the
   shape's work count is a 2D product (const rows × const cols); 1D
   remains the default.
3. Runner/wrapper: choose 2D when the shape declares it.
4. Verify pairs.bv correctness end-to-end, then ledger before/after.

O3 gating note from the M1+O2 profile: the GEMV kernel is memory-bound
(min barely moved with FMA), so float4 loads are the right next lever —
expected to beat any further math-shaping.
