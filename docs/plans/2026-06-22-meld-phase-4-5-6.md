## Phase 4b — Error Messages & Diagnostics

### E001 — No route for field

**Scenario:** Developer declares a meld with explicit routes, but a field on one type has no matching route on the other type.

```
error[E001]: no route for field — `CString` has no route to `Len`
  --> file.bv:5:1
   |
 5 | meld String <:> CString {
   |     Size -> CString .#Size;
   | };
   |
   = `String` has 3 fields: `Ptr`, `Len`, `Cap`
   = `CString` has 1 field: `Ptr`
   = no route maps `String.Len` (bits 64..127) to a CString field or projection
   |
help: add a route for the missing field, or remove the explicit routes and let inference handle it:
   |
   | meld String <:> CString {
   |     Ptr  -> CString.ptr;
   |     Size -> CString .#Size;
   |     Len  -> CString .#Size;
   | };
   |
```

**Implementation (src/typechecker.rs):**

In the `TopLevel::Meld` arm of the second pass, after collecting the meld declaration:

1. Look up the struct fields for both `name_a` and `name_b` via `self.struct_fields`.
2. For each field in type A, check if there's a route in `routes` whose `accessor` matches the field name.
3. If a field has no matching route AND no route exists that could logically cover it (e.g., `Size` covers `Len` for bytes vs chars), emit E001.
4. For projection targets (known names like `Size`, `Ptr`, `Bytes`), check that if they appear in routes, they match known targets for the other type.

**Key insight:** The `@/` bit-range inference handles everything automatically when routes are empty. E001 only fires when the developer provides EXPLICIT routes but the set is incomplete. Inferred melds (no routes) never trigger E001 — they always use `@/` range matching.

**Files to modify:**
- `src/typechecker.rs` — add check in `TopLevel::Meld` arm
- No test infrastructure changes needed — existing `Diagnostic` infra handles it

### E002 — Circular meld

**Scenario:** Developer declares melds that form a cycle in the compatibility graph.

```
warning[E002]: circular meld — `A <:> B`, `B <:> C`, `C <:> A` form a cycle
  --> file.bv:10:1
   |
10 | meld C <:> A;
   | ^^^^^^^^^^^^^
   |
   = existing melds: `A <:> B` (line 3), `B <:> C` (line 7)
   = adding `C <:> A` creates a non-tree cycle in the meld graph
   |
   = note: meld has NO transitive inference, so this cycle does not affect correctness.
   = However, cycles make the declaration graph harder to reason about.
   |
help: remove one of the meld declarations to break the cycle
```

**Implementation (src/type_universe.rs):**

In `build()` during Phase 3 (meld collection), after inserting the new meld:

1. Build an adjacency list from the meld graph (undirected — meld is bidirectional).
2. For each new meld `(A, B)`:
   - Temporarily add the edge `A ↔ B` to the graph.
   - Run DFS from `A` to `B` (skipping the direct `A→B` edge).
   - If a path exists, the graph now contains a cycle involving `A` and `B`.
   - Revert the temporary edge.
3. If a cycle is detected, emit W002 as a warning (NOT an error — cycles don't break correctness since there's no transitive inference).
4. Only emit the warning for cycles of length ≥3 (a duplicate `meld A <:> A` or `meld A <:> B` + `meld B <:> A` is a 2-cycle, which is a harmless duplicate).

**Complexity:** O(V + E) for the DFS, where V = number of distinct types in melds. Typically ≤10 in real programs, so negligible.

**Files to modify:**
- `src/type_universe.rs` — add `detect_circular_meld()` method
- `src/typechecker.rs` — pass cycle warning from TypeUniverse to diagnostics

### E004 — Field type mismatch

**Scenario:** Two fields at the same `@/` bit range have incompatible type annotations.

```
warning[E004]: field type mismatch — `A.Ptr` is `Ptr<Byte>` but `B.Ptr` is `Ptr<Char>`
  --> file.bv:5:1
   |
 5 | meld A <:> B;
   | ^^^^^^^^^^^^^
   |
   = both fields occupy bits 0..63 but have incompatible type annotations
   = the bits are the same width (64 bits), so the meld is valid
   = but operations on the pointee may produce unexpected results
   |
help: add an explicit route to override the default identity mapping:
   |
   | meld A <:> B {
   |     A.Ptr = crack<Ptr<Byte>>(B.Ptr);
   | };
   |
```

**Implementation (src/typechecker.rs):**

When a meld has no explicit routes (inference mode):

1. For each field in type A that shares a bit range with a field in type B, compare their types.
2. If the types differ but have the same width (both are pointers, both are integers of same size), emit E004 as a warning.
3. If the types differ AND have different widths, this is a layout mismatch — emit E003 (size mismatch, already implemented).

**Key insight:** Field type mismatch is only a warning, not an error. The bits are the same width, so the meld is structurally valid. But the different type annotations may surprise developers using the meld.

**Files to modify:**
- `src/typechecker.rs` — add type comparison in meld validation

### E005 — Invalid route expression

**Scenario:** The route's `dest_expr` references a non-existent projection or field on the partner type.

```
error[E005]: invalid route expression — `CString :> NonExistent`
  --> file.bv:6:22
   |
 6 |     String.Len = CString :> NonExistent;
   |                      ^^^
   |
   = `CString` has no projection or field named `NonExistent`
   |
help: available projections on `CString`: `Size`, `Ptr`, `Alias`
```

**Implementation (src/typechecker.rs):**

During typechecking of the route's `dest_expr` (which is evaluated as part of the meld validation):

1. Walk the `dest_expr` tree and find all `Expr::Projection` instances.
2. For each projection's target, check if it's a known projection target (Size, Ptr, etc.) or a `UserDefined`/`UserDefinedWithArg`.
3. For `UserDefined` targets, check against the TypeUniverse's known projection targets for the partner type.
4. For `Expr::FieldAccess(obj, field)` where `obj` is the partner type name, check that the field exists in the partner's struct definition.

**Files to modify:**
- `src/typechecker.rs` — add expression validation for route dest_expr
- No parser changes needed — routes are already parsed

### W001 — Dead cache slot

**Scenario:** A LazyCached field has a cache slot allocated but it's never written. The projection never actually fires in a loop context.

```
warning[W001]: dead cache slot — `strlen` cache on `cs` is never invalidated
  --> file.bv:12:17
   |
 12 |     let len = cs .#Size;
   |                 ^^^^^^^^
   |
   = the cache slot for `cs .#Size` (CString lens) is allocated but never written
   = this wastes 8 bytes in %State
   |
help: if this value is never mutated, declare it `let` instead of mutable
```

**Implementation (src/backend/llvm/mod.rs + src/analysis/transition_graph.rs):**

This requires refining the projection usage analysis:

1. In `compute_projection_usage()`, track whether a projection appears inside a loop or a guard statement (single-execution context).
2. In `assign_field_modes()`, if a field has dual-lens usage but ALL projections are in non-loop contexts, assign `Always` instead of `LazyCached`.
3. If a field has already been assigned `LazyCached` but the analysis later proves no cache writes, downgrade and emit W001.

**Alternative approach:** Post-codegen analysis. After the LLVM IR is emitted, scan for cache stores that are never reached (dead code). If found, emit W001. This is more accurate but harder to implement.

**Files to modify:**
- `src/analysis/transition_graph.rs` — add loop-context tracking for projections
- `src/analysis/mod.rs` — add `is_in_loop_context` helper

### W002 — Unnecessary meld

**Scenario:** Two types have identical `@/` bit-range layouts. The meld router is fully inferred and the explicit routes (if any) are redundant.

```
note[W002]: unnecessary meld — `Float` and `CFloat` have identical @/ ranges
  --> file.bv:5:1
   |
 5 | meld Float <:> CFloat {
   |     Ptr -> CFloat.ptr;
   | };
   |
   = both types have `Bytes = 8`, `Alignment = 8`, and identical field layouts
   = the meld router is fully inferred — no explicit routes needed
   |
help: remove the empty router body for clarity:
   |
   | meld Float <:> CFloat;
   |
```

**Implementation (src/typechecker.rs):**

After checking the meld routes:

1. If the meld has explicit routes, check whether inference would have produced identical routes.
2. If the routes are all identity routes (each accessor matches a field on the partner type at the same position), emit W002.
3. For infer-only melds (no routes), never emit W002 — there's nothing to simplify.

**Files to modify:**
- `src/typechecker.rs` — add route redundancy check

## Phase 3b — Real Materialization

Currently `emit_decay()` always returns identity (the chimera value is passed through unchanged). This is correct for identity cases but wrong when the target type has fields the chimera doesn't directly support.

### String → CString decay (trivial — identity)

CString has one "field": `ptr` (bits 0..63). String stores its data pointer at offset 0 of its heap struct. When viewing a String through the CString lens, `.#Ptr` extracts bits 0..63, which IS the data pointer. So `String → CString` decay is identity — the same pointer.

**Implementation:** None needed. Identity is correct.

### CString → String decay (requires allocation)

String has `{ ptr, len, cap }` (3 fields, 24 bytes). CString has only `ptr` (1 field, 8 bytes). When a CString value needs to be materialized to String:

1. Extract `ptr` from the CString (bits 0..63, same as `.#Ptr`).
2. Compute `len = strlen(ptr)` — call the `__strlen__` runtime intrinsic.
3. Allocate a 3-field String struct on the heap: `{ ptr, len, cap = len }`.
4. Return the pointer to the allocated struct.

The decay IS NOT identity — it requires a heap allocation and a strlen call.

**Implementation (src/backend/llvm/emit_expr.rs):**

The `emit_decay` function needs to handle the case `backing = "CString"` → `target = "String"`:

```rust
if backing == "CString" && target_name == "String" {
    // Materialize CString → String: { ptr, len, cap }
    // 1. Extract ptr via .#Ptr on the source
    let ptr_reg = self.emit_direct_projection(out, val, "Ptr", indent);
    // 2. Compute len via __strlen__(ptr)
    let len_reg = format!("%mt_len{}", self.txn_counter);
    writeln!(out, "{}{} = call i64 @__strlen__(i64 {})", indent, len_reg, ptr_reg.name);
    // 3. Allocate 3 × i64 on the heap
    let alloc_reg = format!("%mt_alloc{}", self.txn_counter);
    writeln!(out, "{}{} = call i8* @malloc(i64 24)", indent, alloc_reg);
    let struct_ptr = format!("%mt_sp{}", self.txn_counter);
    writeln!(out, "{}{} = bitcast i8* {} to i64*", indent, struct_ptr, alloc_reg);
    // Store ptr at [0], len at [1], cap at [2]
    writeln!(out, "{}store i64 {}, i64* {}, align 8", indent, ptr_reg.name, struct_ptr);
    // ... GEP + store for len and cap
    return TypedRegister { name: struct_ptr, ty: Type::Custom("String".into()) };
}
```

**Files to modify:**
- `src/backend/llvm/emit_expr.rs` — extend `emit_decay()` with type-pair-specific materialization
- `src/backend/llvm/mod.rs` — ensure `@__strlen__` and `@malloc` are declared

### Wire decay into FFI boundaries

When a chimera value is passed to a `frgn` function call, it must be materialized to the parameter's declared type before the call.

**Implementation (src/backend/llvm/emit_expr.rs):**

In the `Expr::Call(fn_name, args)` handler for foreign calls:

```rust
for (arg, param_ty) in args.iter().zip(param_types.iter()) {
    let arg_reg = self.emit_expr(out, arg, indent);
    let arg_reg = self.emit_decay(out, &arg_reg, Some(param_ty), indent);
    // ... emit argument for the call
}
```

This is conceptually simple but requires the FFI call site to have access to parameter types. Currently, `frgn` call emission is in `emit_expr.rs` in the `IntrinsicCall` handler. The parameter types are available from the foreign binding signature.

**Files to modify:**
- `src/backend/llvm/emit_expr.rs` — add decay before foreign calls

### Wire decay into struct field stores

When a chimera value is stored into a struct field (via `FieldAccess` on a struct instance), it must be decayed to the field's declared type.

**Implementation (src/backend/llvm/emit_expr.rs):**

In the `Expr::FieldAccess` write path (the `ArrowMut`/assignment handling):

```rust
if let Some(field_ty) = self.field_type_of(struct_type, field_name) {

}
```

## Phase 5 — Performance Optimization

### Per-(field, target) cache slots

**Current state:** One cache slot per LazyCached field. All projections on that field share the same cache, which means the last computed projection overwrites the previous one.

**Problem:** If a loop projects both `.#Size` and `.#Ptr` on the same CString field, each projection evicts the other's cached value. The cache is effectively useless — every access is a miss.

**Fix:** Change `cache_slots` from `HashMap<String, (usize, usize)>` (one per field) to `HashMap<String, HashMap<String, (usize, usize)>>` (one per field per projection target). Each projection target gets its own cache slot + valid flag.

**Implementation (src/backend/llvm/mod.rs + src/analysis/mod.rs):**

1. Change `cache_slots` type:
   ```rust
   // Old: field → (cache_idx, valid_idx)
   pub(crate) cache_slots: HashMap<String, (usize, usize)>,
   // New: field → target_name → (cache_idx, valid_idx)
   pub(crate) cache_slots: HashMap<String, HashMap<String, (usize, usize)>>,
   ```
2. In `apply_field_modes()`, allocate one cache slot per projection target instead of one per field.
3. In `try_cached_projection()`, look up `cache_slots[field_name][target_name]` instead of just `cache_slots[field_name]`.

**Impact on %State size:** Each additional projection target adds 8 + 1 = 9 bytes. For a field with 2 targets, that's 18 bytes instead of 9. This is acceptable for the Hot Dual path.

**Files to modify:**
- `src/backend/llvm/mod.rs` — change `cache_slots` type
- `src/backend/llvm/emit_expr.rs` — update `try_cached_projection`
- `src/backend/llvm/emit_toplevel.rs` — update cache init stores
- `src/backend/llvm/emit_stmt.rs` — update cache invalidation

### Dead cache slot removal (W001 as optimization)

**Approach:** After codegen, scan the emitted LLVM IR for cache validity stores. If a cache slot's valid flag is never set to 1 (no cache miss path), the cache is never used. Remove it.

This is the same analysis as W001 but applied as an optimization pass before LLVM optimization.

**Implementation (src/backend/llvm/mod.rs):**

A new pass `eliminate_dead_cache_slots()` that runs after `apply_field_modes()` but before the main emission:

```rust
fn eliminate_dead_cache_slots(&mut self) {
    let mut to_remove: Vec<String> = Vec::new();
    for (field, targets) in &self.cache_slots {
        for (target, _indices) in targets {
            if !self.projection_usage_in_loop.contains(&(field.clone(), target.clone())) {
                to_remove.push(field.clone());
            }
        }
    }
    for field in to_remove {
        self.cache_slots.remove(&field);
        self.field_modes.insert(field.clone(), FieldMode::Always);
    }
}
```

This requires tracking which (field, projection) pairs appear in loop contexts. See W001 analysis above.

**Files to modify:**
- `src/backend/llvm/mod.rs` — add `eliminate_dead_cache_slots()` pass
- `src/analysis/transition_graph.rs` — add loop context tracking

### Merge Short path when no cache needed

**Current state:** `assign_field_modes()` is conservative — if a field has ≥2 different projection targets, it gets `LazyCached` even if the projections are in different transactions or non-loop contexts.

**Fix:** Check whether the dual-target projections appear in the SAME loop body. If they're in different scopes, the cache slot is never reused and just wastes space.

**Implementation (src/analysis/transition_graph.rs):**

In `compute_projection_usage()`, add scope tracking:

```rust
pub struct ProjectionUsageEntry {
    pub targets: HashSet<String>,
    pub in_same_loop: bool,  // true if ≥2 targets in same loop body
}
```

Then in `assign_field_modes()`, only assign `LazyCached` when `in_same_loop` is true.

**Files to modify:**
- `src/analysis/transition_graph.rs` — add scope tracking
- `src/analysis/mod.rs` — update `FieldMode` assignment logic

### Remove stale cache on LICM hoist

**Scenario:** LLVM's Loop Invariant Code Motion (LICM) may hoist a projection out of a hot loop. After LICM, the projection is computed once before the loop and never inside it. The cache miss+store inside the loop becomes dead code.

**Problem:** The cache slot was allocated assuming the projection would be computed inside the loop. After LICM, the cache is unnecessary — the hoisted value is already in an SSA register.

**Fix:** This is an LLVM optimization, not a Briev compiler optimization. The cache code pattern (`load valid → branch → load cached / compute + store → phi`) is recognized by LLVM's optimizer and LICM can eliminate the loop-invariant branch. However, we should verify this with LLVM's `-pass-remarks` infrastructure.

**Implementation:** Add a benchmark to test that LICM eliminates the cache check for loop-invariant projections. If it doesn't, add an LLVM pass pipeline comment (`!llvm.loop.licm.enable` metadata) or restructure the emitted code to be more LICM-friendly.

**Files to modify:**
- `benchmarks/build_and_bench.sh` — add meld cache LICM test
- `src/backend/llvm/emit_expr.rs` — optionally emit `!llvm.loop.licm` metadata

## Phase 6 — Generics

### Parser changes

**Syntax:** `meld List<T> <:> Vec<T>;`

The `<T>` after each type name declares a generic type parameter. Multiple parameters: `meld HashMap<K, V> <:> Dict<K, V>;`

**Implementation (src/ast.rs + src/parser.rs):**

1. Add `type_params: Vec<String>` to `MeldDeclaration`.
2. In `parse_meld_decl()`, after parsing `name_a`:
   - If next token is `<`, parse a comma-separated list of identifiers followed by `>`.
   - Store these in `type_params_a`.
   - Same for `name_b` after `<:>`.
3. Type parameters must match between A and B (same names, same order).

```rust
pub struct MeldDeclaration {
    pub name_a: String,
    pub type_params_a: Vec<String>,  // NEW
    pub name_b: String,
    pub type_params_b: Vec<String>,  // NEW
    pub routes: Vec<MeldRouteDef>,
    pub span: Option<Span>,
}
```

**Files to modify:**
- `src/ast.rs` — add type_params fields to MeldDeclaration
- `src/parser.rs` — parse generic parameters in meld

### TypeUniverse changes

**Storage:** Generic melds cannot use the flat `HashMap<(String, String), MeldDeclaration>` structure because the key depends on the type parameter. Instead, store generic melds separately:

```rust
pub struct TypeUniverse {
    pub types: HashMap<String, ResolvedType>,
    pub resolution_order: Vec<String>,
    pub melds: HashMap<(String, String), MeldDeclaration>,           // concrete
    pub generic_melds: HashMap<(String, String), GenericMeld>,       // NEW: generic
    pub concretized: RefCell<HashMap<(String, String), MeldDeclaration>>, // NEW: cached
    pub meld_errors: Vec<String>,
}
```

```rust
pub struct GenericMeld {
    pub type_params: Vec<String>,
    pub name_a: String,     // e.g., "List"
    pub name_b: String,     // e.g., "Vec"
    pub routes: Vec<MeldRouteDef>,
    pub span: Option<Span>,
}
```

The key `(String, String)` for generic melds uses the type CONSTRUCTOR name (e.g., "List") without parameters.

### Concretization

When `find_meld(a: &str, b: &str)` is called with concrete types like `List<Int>` and `Vec<Int>`:

1. Parse the type parameters from the concrete type names: `List<Int>` → constructor `List`, param `Int`.
2. Check if `generic_melds` has an entry for `(List, Vec)`.
3. If found, check the cache in `concretized`.
4. If not cached, concretize: substitute `T → Int` in all route expressions and store the result in `concretized`.
5. For substitution: walk each route's `dest_expr` and replace `Expr::Identifier("T")` with `Expr::TypeRef("Int")` or keep as-is (T is only used in internal representations, not in the actual route logic).

**Implementation (src/type_universe.rs):**

```rust
fn concretize_meld(
    generic: &GenericMeld,
    params_a: &[String],  // concrete params for A
    params_b: &[String],  // concrete params for B
) -> MeldDeclaration {
    // Build substitution map: T → Int
    let mut subst: HashMap<String, String> = HashMap::new();
    for (param, concrete) in generic.type_params.iter().zip(params_a.iter()) {
        subst.insert(param.clone(), concrete.clone());
    }
    // Replace type params in name_a and name_b
    let name_a = concrete_type_name(&generic.name_a, params_a);
    let name_b = concrete_type_name(&generic.name_b, params_b);
    // Concretize routes (substitute type params in route expressions)
    let routes = generic.routes.iter().map(|route| {
        let dest_expr = substitute_type_param(&route.dest_expr, &subst);
        MeldRouteDef { accessor: route.accessor.clone(), dest_expr }
    }).collect();
    MeldDeclaration { name_a, name_b, routes, span: generic.span }
}
```

The route expressions reference bits (`@0..63`) and intrinsics (`strlen#`) which do NOT depend on T. So substitution is only needed for type name references in the expression, which generic meld routes should avoid.

### Proof of structural equivalence

For `meld List<T> <:> Vec<T>`:

> `List<T>.Ptr = Vec<T>.Ptr @/0..63` ✓  
> `List<T>.Len = Vec<T>.Len @/64..127` ✓  
> `List<T>.Cap = Vec<T>.Cap @/128..191` ✓  

Proof: On a 64-bit architecture, `ptr`, `len`, and `cap` are each 64 bits regardless of T. The element type T only affects what `ptr` points to, not the pointer itself. Therefore, the layout of `List<T>` and `Vec<T>` is identical for any T.

Implementation: The proof engine need not do anything special for generic melds — the structural equivalence is a property of the type definitions themselves. If `List<T>` and `Vec<T>` are defined with identical field types, the proof engine will automatically prove equivalence.
